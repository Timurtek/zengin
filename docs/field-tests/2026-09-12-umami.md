# Field test: umami-software/umami

**Date** 2026-09-12. **Subject** [umami-software/umami](https://github.com/umami-software/umami) at `ca661c7`: Next 16, React 19, 521 TSX files and 11 CSS files under `src/`, 316 imports from `@umami/react-zen@0.249.0`. Not a shadcn project: react-zen is Umami's own component library, shipped as an npm package with Base UI behavior, `tailwind-variants` for variants, a `styles.css` of semantic custom properties (`--surface-base`, `--text-primary`, `--status-error`, oklch greys) and a precompiled `styles.full.css` of Tailwind utilities that the app uses by class name. No Tailwind in the app itself.

The question this time: can the engine check a codebase whose system is not shadcn and not Zengin UI, with no hand-written definitions, and does it say anything true about it.

## Method

A new adapter, `@zengin/adapter-css`, reads an installed package instead of a project: `zengin init --from package @umami/react-zen`, then `zengin check`. Tokens come from the package's stylesheet with their variable names kept (`$extensions.zengin.cssVar`), so the engine speaks the project's vocabulary: a fix says `var(--surface-base)`, not a renamed token. The component manifest comes from the package's `.d.ts`: `declare function X(props: XProps)` says the component exists, the props type says what it takes, the `tailwind-variants` constant named for it says which `variant` and `size` values it accepts. The generated config points `classes.css` at `styles.full.css`, so `className="w-full max-w-md"` resolves to declarations without a class compiler. Every violation read and classified by hand, as before.

| Classification | Count | What |

Two of the adapter's first choices were also wrong before any violation showed: it picked `styles.full.css` as the theme sheet, because it defines more variables (Tailwind's whole palette) than `styles.css` does, and it skipped 23 components declared as `ForwardRefExoticComponent<HTMLAttributes<HTMLDivElement>>` or with an inline props type. Both were fixed before the first run counted.

## Changes made

Engine, with regression tests in `packages/engine/test/engine.test.ts`:

- Stylesheets named in `classes.css` are indexed as `external` class resolutions: a system that ships precompiled utilities resolves class names the project's own CSS never defines. Foundation rules judge their declarations at the use, as they do for compiled utilities; `token-reference` leaves them alone, since a shipped utility references its own system's variables.
- `$extensions.zengin.cssVar` on a token sets its variable name. Definitions derived from an existing system keep that system's names.
- A manifest may declare `passthrough`: the types whose props a component forwards without enumerating them (`@base-ui/react/popover#Popover.Positioner.Props`). `unknown-prop` does not run on such a component, and the reason is on record in the manifest. Enum values are still checked.
- A "nearest" spacing fix is offered only when the neighbour is within 4px or half the value. Beyond that the scale steps go in the note and the confidence is `none`.
- A hex with a zero alpha channel, or an `rgb()`/`hsl()` with alpha 0, is `transparent`, not a color literal.

Adapter (`packages/adapter-css`, 16 tests against a trimmed react-zen fixture and a synthetic installed package):

- The theme sheet is the stylesheet that is mostly custom properties (variables per class rule), not the one with the most variables. The utility sheet is the largest of the rest.
- Components are read from `declare function`, `declare const X: ForwardRefExoticComponent<...>` and `FC<...>`. Props come from the parameter type, followed through interfaces, aliases, intersections, `Omit`/`Partial`/`Pick`, and `VariantProps<typeof x>`. `HTMLAttributes<HTMLButtonElement>` anywhere in the chain becomes `extends: button`.
- A type declared in another package, reached through an import (`Popover$1.Positioner.Props`, `UseFormProps`, `ProgressRoot.Props`), becomes a `passthrough` entry named by its source, `@base-ui/react/progress#ProgressRoot.Props`. React's own helpers (`react.RefAttributes`, `react.HTMLAttributes`) are read by their last segment and never count as passthrough.
- `as`, `render`, `slot` and `asChild` are props like any other.
- Project stylesheets that define `:root` custom properties are written into `scope.foundations`.

**False positives: 0 of 147 by hand classification. The adapter needed no hand edits; 158 components and 53 tokens derived from the package alone, 55 components carrying a `passthrough` record of the Base UI, cmdk or react-hook-form type they forward.**

## What it says

- The engine is not tied to shadcn or to Zengin UI. Given a stylesheet of custom properties and a `.d.ts`, it checks a codebase in that system's own words, and the first non-shadcn run found the same three things the shadcn runs found: hand-written palette colors where semantic tokens exist, pixel spacing where the system has a scale, and one raw button.
- It also found two real defects a linter would not: an attribute that silently reaches the DOM (`flex-direction`), and a `var()` whose fallback is what actually renders (`--color-danger`).
- What a package's types cannot say is now said out loud rather than guessed. `passthrough` is the adapter admitting where the manifest ends; the alternative was 66 false unknown-prop reports or a silent skip.
- Three field tests, 0 false positives after fixes on each, 422 violations classified by hand in total.
